# Flutter Testsmith

An AI-native testing platform for Flutter. Where a conventional end-to-end
tool validates `user action -> expected result`, this one is being built to
validate the whole chain:

```
user action -> navigation -> API request -> API response -> app state
   -> widget tree -> UI field values -> Figma spec -> screenshot
   -> visual comparison -> AI analysis -> result
```

**Status: 12 phases. Phase 12 was a hardening phase, and its report
says plainly what is and is not production-ready** - see
[docs/PHASE_12_ACCEPTANCE.md](docs/PHASE_12_ACCEPTANCE.md), which marks
every capability PASS, PARTIAL, FAIL or NOT IMPLEMENTED against a named
piece of evidence, and ends with twelve limitations and a
recommendation.

`testsmith run` drives a flow on a device,
compares API values against what the UI actually shows, applies declarative
business rules, compares the screen against a normalised Figma frame
(presence, element kind, geometry, ordering, typography and colour),
compares the screenshot with a committed baseline, writes `result.json` and
`report.html`, and can ask a language model to explain whatever failed. See
[docs/IMPLEMENTATION_PLAN.md](docs/IMPLEMENTATION_PLAN.md).

On the Samsung SM-M127G, the seven-screen example runs end to end with
**102 deterministic checks and nothing failing**; the same screen
compared against its baseline five times running measured **0.000%
differing, ssim 1.0000, zero false positives**, and a seeded defect was
caught **3 times out of 3**. Those numbers are from
[docs/evidence/](docs/evidence/), generated by the runs that produced
them.

## The thing it does

```
$ testsmith run examples/ecommerce_app/tests/product.yaml -d <serial> \
      --mock-api 8080 --dart-define=SEED_PRICE_BUG=true

  > tap "home.open_product"
  > expect to be on "/product/details"
  > validate the screen (automatic)
    OK  ui-presence      product.price: present
    X   api-to-ui        product.price: product.price.text does not match
                         response.price. API returned 90; currency(INR)
                         gives "Rs 90"; the UI shows "Rs -310".
    OK  figma-geometry   product.image: matches the design geometry
    OK  figma-typography product.name: matches the design typography
    X   visual           product.price differs by 17.901% of its own area
                         (tolerance 5.000%)
    -   figma-geometry   vertical positions were not compared: the design
                         frame is 402x1198 and the viewport is 384x805, an
                         aspect difference of 30%.

  /product/details  FAIL  45 ok, 2 failed, 3 skipped, 0 errored
```

Three values in that API failure, not one. The raw API number, what the
declared transformation says the app *should* render, and what it actually
rendered - which is what separates a data bug from a formatting bug.

And note the last line: a check that could not honestly be made says so,
rather than passing quietly or failing loudly. `skip` is not `pass`.

## The governing principle

**The deterministic engine decides. AI explains, suggests, and prioritises.**

A pass/fail verdict never carries a confidence score, and AI never mutates a
user-authored file. Both rules are structural rather than conventions. See
[docs/ARCHITECTURE.md](docs/ARCHITECTURE.md).

## Quick start

```bash
dart pub get                      # one resolve for the whole workspace
cp .env.example .env              # optional: Figma, AI and auth credentials

dart run packages/flutter_testsmith/bin/testsmith.dart doctor
dart run packages/flutter_testsmith/bin/testsmith.dart devices
dart run packages/flutter_testsmith/bin/testsmith.dart preflight <suite.yaml> -d <serial>
dart run packages/flutter_testsmith/bin/testsmith.dart inspect -d <serial>
dart run packages/flutter_testsmith/bin/testsmith.dart smoke -d <serial> \
    --tap-id home.open_product
```

`smoke` launches the example app, attaches over the Dart VM Service,
completes a handshake, recovers the events emitted before it could
subscribe, captures the UI tree, taps an element **by its semantic id**,
and prints the correlated event stream.

`preflight` answers "could this machine test anything?" before a suite
spends minutes finding out - a missing device, a revoked permission, an
occupied fixture port. It exits 2 when something blocks, which is the
code an unevaluable test has always produced. See
[docs/E-04_TEST_ENVIRONMENT.md](docs/E-04_TEST_ENVIRONMENT.md).

`inspect` prints the semantic tree of the current screen. Add
`--tap <id>` to navigate first, or `--json <path>` to save the snapshot.

## What the UI tree looks like

Captured from the device. The sign-in screen filters 365 elements down
to 17:

```
UI tree: /login

  Tree

      Text "Email" (24,112 42.1x16)
    TextField #login.password "[REDACTED]:24" enabled (24,172 336x56)
      Text "Password" (24,180 74.7x16)
    FilledButton #login.submit [Sign in] enabled (24,252 336x48)
      Text "Sign in" (170.3,266 43.3x20)
    Text #login.sdk_status "test instrumentation: ARMED" (24,765.3 336x16)
    AppBar (0,0 384x80)
      Text "Sign in" (16,38 65.9x28)

  test ids (4): login.email, login.password, login.submit, login.sdk_status
```

Bounds are Flutter **logical** pixels. `tap-id login.submit` converts the
centre of those bounds using the ratio recorded in the same snapshot,
giving `PhysicalPoint(360, 518)` - which is where the button actually is.

`[REDACTED]:24` is a field the application obscured on screen. The tree
leaves the process - as an event, and through `testsmith inspect --json` -
so an obscured field is masked at capture, keeping only its length. That
was a real leak until Phase 12: network capture had been redacting since
Phase 3 and nothing had ever looked at this path, so the tree carried
the example's password in plaintext while the screen showed dots.

An element laid out **below the fold** is refused rather than tapped,
with the measurement that explains it. Found on a device: the Add to
Cart button sits at the foot of a 1198pt page, the tap went to a y
outside the screen, Android delivered it to nothing, and the run failed
four steps later on an `expectScreen` that had no idea why.

Three numbers in there are the point of the phase:

- **recovered from ring buffer: 2** - `postEvent` is fire-and-forget, so
  session start and the first screen entry are emitted before any runner can
  subscribe. Without the SDK-side ring buffer the first screen of every run
  is a race.
- **duplicates discarded: 1** - DDS replays buffered events to a newly
  attached client *and* the handshake drains the ring buffer, so pre-attach
  events genuinely arrive twice.
- **dpr at attach 1.0 vs settled 1.875** - the handshake completes before
  the first frame, when the Android view still reports a placeholder ratio.
  Any coordinate conversion must read the ratio at use time.

## Comparing a screen with its Figma frame

`validateScreen: { figma: true }` compares the captured tree against the
normalised design in `<app>/figma/*.json`, matched by screen id. Each check
reports separately, so a report says *which* part of the design disagrees:

| Check | Asks |
|---|---|
| `figma-structure` | is every mapped design element on the screen, once, and visible? |
| `figma-type` | does a TEXT node render text, and an IMAGE node paint an image? |
| `figma-geometry` | is it the right size, in the right place? |
| `figma-order` | do the elements run top-to-bottom in the design's order? |
| `figma-typography` | do the resolved font size, weight and family match? |
| `figma-colour` | does the painted colour match, within a channel tolerance? |

Thresholds live per screen in the mappings file, because a dense form
needs a tighter tolerance than a hero banner:

```yaml
figma:
  positionPx: 6      # default 4
  sizePx: 4          # default 3
  text: strict       # default ignore - a design holds placeholder copy
  reportUnexpected: true   # default false
```

Three behaviours are worth knowing about, because each exists to avoid a
class of false failure:

- **The design is scaled to the device before anything is compared**, by
  width. Where the frame and the viewport are differently *shaped* -
  a tall scrolling frame against a phone screen - vertical position is
  reported as skipped rather than failed. See
  [ADR-0007](docs/adr/0007-design-projection.md).
- **Design copy is ignored by default.** A design says `Product Name`;
  the running app shows whatever the API returned. Opt in with
  `text: strict` for static copy such as button labels and headings.
- **A label inside a widget still counts.** The test id belongs on the
  `FilledButton`; the design's TEXT node describes the `Text` inside it.
  Typography, colour and copy are read from whichever descendant actually
  renders the text - provided there is exactly one, since two would make
  the choice a guess.

## Visual regression

`validateScreen: { visual: true }` compares the screenshot with the
accepted baseline in `<app>/visual_baselines/`, committed and reviewed like
any other file. A first run records one and reports `skip` — it cannot
detect a regression, so it does not claim to.

Three gates, because one number cannot do the job:

| Gate | Default | Catches |
|---|---|---|
| whole-screen differing ratio | 0.2% | large localised change |
| per-element differing ratio | 5% of that element | a small element changing |
| mean SSIM | 0.98 | change too thin for the channel threshold |

The middle one earns its place. The seeded price regression below changed
**15.6% of the price element but only 0.04% of the screen** — invisible to a
whole-screen tolerance, unmistakable against the element's own area.

```yaml
visual:
  channelDelta: 8          # antialiasing moves channels; 0 fails every run
  maxDifferingRatio: 0.002
  ignoreRegions:           # logical pixels, so density does not matter
    - x: 0
      y: 0
      width: 9999
      height: 24           # the status bar: its clock is not a regression
```

Measured on a physical device in Phase 12, after ignoring **both**
system bars:

```
five identical runs    0.000% differ, ssim 1.0000     0 false positives
seeded regression      product.price differs by 17.901% of its own area
                       detected 3 runs out of 3, identical each time
```

Both bars mattered, and the second one was missed for five phases. The
status bar's clock made ~480 pixels differ on every run; the navigation
bar made another 723, a third of the whole tolerance budget, spent on
something that is never a regression. A negative `y` in an ignore region
is measured from the bottom of the image, so a system bar can be written
down without hard-coding a device height:

```yaml
    - x: 0
      y: -32          # the navigation bar, anchored to the foot
      width: 9999
      height: 32
```

Details in [ADR-0008](docs/adr/0008-visual-comparison.md) and the
measurements in [docs/evidence/device-runs.md](docs/evidence/device-runs.md).

Baselines are never updated automatically — a store that re-records on
difference is a suite that can never fail the same way twice.
`--update-visual-baselines` is explicit, and accepts whatever is on screen.

## AI analysis

`testsmith run ... --ai` asks a model to explain whatever failed. It runs **after**
the verdict is computed, on a finished result, and returns a copy with an
explanation attached — so there is no code path from a model's output to a
pass or fail. A test asserts that a model insisting everything is fine leaves
the run failed.

Three claim levels, and the distinction is the point:

| Level | Means |
|---|---|
| `confirmed_failure` | restates measured facts, no causal claim |
| `probable_cause` | asserts a cause the data supports |
| `hypothesis` | asserts a cause the data does not establish |

An unrecognised value parses to `hypothesis` — the weakest claim. Defaulting
the other way would let a malformed reply promote a guess to a certainty.

On the seeded price regression, unedited:

```
AI analysis (groq/openai/gpt-oss-120b - explanation, not a verdict)
  The product details screen shows an incorrect price, causing both
  data-validation and visual-diff failures.

    [confirmed]       api-to-ui product.price
      The API returned price 90 (displayed as "Rs 90" for INR) but the UI
      rendered "Rs -,310" for product.price.
    [probable cause]  api-to-ui product.price      (model confidence 92%)
      Likely an incorrect formatting or data-binding implementation,
      because the UI shows a completely different number rather than a
      simple rounding error.
    [probable cause]  visual                       (model confidence 88%)
      Likely caused by the same price rendering error identified in the
      api-to-ui failure.
```

Two independent validators, one root cause — which is the thing a
deterministic engine cannot do, and the reason this layer exists.

### Changing the model

The provider is configuration, not code. `ai.yaml`:

```yaml
provider: groq                 # or openai, openrouter, together, ollama, custom
model: openai/gpt-oss-120b
apiKeyEnv: GROQ_API_KEY        # the NAME of the variable, never the key
temperature: 0                 # two runs should tell the same story
```

Running against a local Ollama instead is the whole diff:

```yaml
provider: ollama
model: llama3
```

`--ai-provider` and `--ai-model` override the file for one run. Anything
speaking the OpenAI chat-completions shape works; Anthropic and Gemini use a
different wire format and are **rejected with an explanation** rather than
sent a body they cannot parse.

Writing `apiKey:` into `ai.yaml` is a parse error — a secret in that file is a
secret in your repository. Keys resolve from the environment first, then
`.env` (gitignored).

**A model outage is never a test failure.** No key, provider down, or an
unparseable reply all report as *unavailable* and leave the verdict untouched.
Bodies and headers are never sent: redaction strips secrets at capture, but
not sending the payload is the cheaper guarantee. See
[ADR-0009](docs/adr/0009-ai-analysis.md).

## Naming the API state a test needs

A test that asserts "the screen says Out of stock" is only a test when
the API actually says the product is unavailable. A flow names the state
it needs, and the runner refuses to run without it:

```yaml
appId: com.example.ecommerce_app
flow: product_out_of_stock
fixture: product_out_of_stock     # mock_api/scenarios/*.json

steps:
  - launchApp
  - tap:      { id: login.submit }
  - tap:      { id: home.open_product }
  - validateScreen
  - expectElement: { id: product.add_to_cart, enabled: false }
  - expectElement: { id: product.unavailable, visible: true }
```

A scenario is a **delta** against `default.json`, so saying "this product
is unavailable" does not mean restating the cart, the login and the
checkout:

```json
{
  "name": "api_500_server_error",
  "inherits": "default",
  "routes": { "GET /products/123": { "status": 500 } }
}
```

Routes can return any status, delay past the client's timeout, or send a
body that is deliberately not JSON - so a timeout, a 500 and an
unreadable reply are three different tests rather than one.

This exists because of a defect Phase 12 found in its own first hour.
Seven generated scenarios were committed, named `api_404_not_found`,
`api_timeout`, `empty_highlights_list` and so on - and every one of them
declared a precondition **nothing could arrange**, because the mock API
served one static file. They parsed. They referenced real ids.
Approving any of them would have added a test that runs against the
happy path under an edge-case name and passes, reporting coverage that
did not exist.

`testsmith generate` is now given the list of fixtures that exist, and a
proposal naming one that does not is rejected.

### Serving a picture, so a screen with remote images can be photographed

A screen drawing its images from somebody else's CDN cannot be
photographed deterministically: the bytes are outside this repository's
control and the fade-in is timed by their network. A route can answer
with bytes instead of text:

```json
"GET /fixtures/outlet.png": {
  "status": 200,
  "headers": { "content-type": "image/png" },
  "bodyBase64": "iVBORw0KGgoAAAANSUhEUg..."
}
```

Decoded at parse time, so a corrupt fixture fails when the file is read
rather than reaching the screen as a broken-image placeholder - which
photographs perfectly well and explains nothing. Nothing is guessed about
the content type: a scenario that sends bytes says what they are.

## Asserting on the API inside a UI flow

Every other check is a statement about a screen, and a screen rendered
from a **failed** request photographs perfectly well. `expectApi` asserts
on the exchange the application actually made, at a point in the flow:

```yaml
- tap: { id: nav.orders }
- expectScreen: { id: /orders, timeoutMs: 15000 }

- expectApi:
    endpoint: GET /api/requests/*
    status: 200
    occurrence: last
    expect:
      - path: data
        count: 3
      - path: data.0.currentStatus
        equals: DELIVERED
      - path: token
        present: true

- waitForSettle
- validateScreen: { visual: true }
```

| Key | |
|---|---|
| `endpoint` | `METHOD /path`; a segment may be `*` |
| `status` | **required** - a step that says nothing about the answer passes against a 500 |
| `occurrence` | `only` (default, refuses to choose), `first`, `last` |
| `expect` | a list of `path` plus exactly one of `equals`, `count`, `present` |

It reads the **SDK's** capture, not the fixture server's log: the two
answer different questions, and a response the app served from its own
cache appears in one and not the other.

`present:` is there so a token can be asserted without being written
down. No response body reaches the report - a report is a file people
paste into tickets.

## The deterministic end-to-end suite

```bash
./scripts/run_e2e.sh              # every screen, against committed fixtures
./scripts/run_e2e.sh --negatives  # and the flows that must fail
```

No backend, and no network beyond the loopback interface the fixture
server binds to. A negative flow that **passes** fails the suite: a suite
that only ever checks things pass cannot tell a working check from a
check that no longer runs.

Needs a device attached. See
[docs/STOP_3_DETERMINISTIC_E2E.md](docs/STOP_3_DETERMINISTIC_E2E.md).

## Which tests a change makes worth running

```
$ testsmith impact --since main

Changed files
  examples/ecommerce_app/lib/product_details_screen.dart

Selection
  1 of 2 flow(s) selected from 1 changed file(s)

  RUN  product_details  examples/ecommerce_app/tests/product.yaml
        touches .../product_details_screen.dart (/product/details)
  skip home  no changed file touches it
```

Attribution comes from what files declare — a `route` constant, a `TestKey`,
the `screen:` a mappings or design file names — matched against what each
flow asserts it reaches. `--json` emits the same thing for a CI job to act
on; `--changed <path>` answers "what *would* this select?" without a commit.

**This is deterministic, deliberately.** It decides what gets *tested*, so a
wrong answer doesn't produce a visible failure — it produces a regression
nobody looked for. A model may later be asked to **widen** a selection; it
must never narrow one.

Hence the governing rule: **a flow is excluded only on positive evidence
that every changed file is unrelated to it.** One unaccounted-for file
selects everything, and says which file and why:

```
running everything: nothing is known about lib/widgets/spinner.dart,
so no flow can be ruled out
```

Changing the router, a manifest, a bundled asset, or the test platform
itself does the same — each with the reason that actually applies rather
than a generic fallback. Documentation changes select nothing.

## Proposing tests, without letting a model write one

```
$ testsmith generate

Proposing scenarios for /product/details
  groq/openai/gpt-oss-120b · 13 element(s) · 2 existing flow(s)

  proposed api_404_not_found  error
      Ensures the screen gracefully handles a 404 for a missing product
      needs: API returns HTTP 404 for product id 123
  proposed discount_exceeds_price  boundary
      Handles a discount larger than the price, which could otherwise
      show negative pricing
      needs: API returns "price":90 and "discount":120

7 proposal(s). None of them will run: each is marked `status: proposed`.
```

The scenarios come from a real fixture response, the screen's mappings and
rules, and the flows that already exist — so proposals aim at what is *not*
covered.

**Nothing generated can run.** The generator stamps `status: proposed` on
every flow — not the model, and any status the model wrote is replaced,
because asking politely is not a control. The mark is on the flow rather
than the folder, so pointing the runner at the file still refuses:

```
$ testsmith run tests/proposed/api_404_not_found.yaml

"api_404_not_found" is marked `status: proposed`.
It was generated, and nobody has reviewed it. Read it, arrange whatever
state it needs, then delete the `status: proposed` line to accept it.
```

Accepting is a human editing the file. This mirrors AI mapping suggestions,
which land under `suggested:` and stay inert until promoted by hand.

Two validations run before anything is written, because syntax is not sense:
the flow is **parsed** (a generated file can never break the suite) and its
references are **checked against ids that actually exist**. The first real
batch expected screen `product_details` where the id is `/product/details` —
which parses perfectly and fails only once someone runs it on a device.

## Package layout

One package, `flutter_testsmith` (`packages/flutter_testsmith/`), holds the
whole implementation (ADR-0011). Its components are directories with their
own public library where one is useful:

| Component | Location | Purpose |
|---|---|---|
| SDK | `lib/flutter_testsmith.dart`, `lib/src/` | In-app instrumentation: session, navigation, semantic test ids, UI tree inspection, network capture, redaction, production gating. The one library an application imports. |
| Protocol | `lib/protocol.dart`, `lib/src/protocol/` | Versioned event and handshake contract. No dependency beyond `meta`, because it is linked into apps under test; re-exported by the SDK. |
| Engine | `lib/engine.dart`, `lib/src/engine/` | Transport, device control, session and API correlation, element lookup, validation, reporting. **Its code never imports Flutter.** |
| CLI | `bin/testsmith.dart`, `lib/src/cli/` | The `testsmith` binary, run as `dart run flutter_testsmith:testsmith`. Argument parsing and formatting only; no public library. |
| Figma | `lib/figma.dart`, `lib/src/figma/` | Figma REST client and design normalisation into a comparable spec. |
| AI | `lib/ai.dart`, `lib/src/ai/` | Provider-agnostic chat completions. Knows nothing about testing, so the provider is a config value. |

`scripts/check_dependencies.dart` proves over the import graph that the
SDK reaches no engine, CLI, Figma or AI code, and that none of those, nor
the protocol, reaches Flutter.

`examples/ecommerce_app` is the seven-screen example: login, home,
products, product details, cart, checkout, order success. Every screen has
loading, error, empty and data states, null-tolerant parsing, and
conditional sections. Product Details implements the `Product Details`
Figma frame, expressing its margins as fractions of the 402pt design width
so the layout projects onto any device exactly.

## Adding the SDK to an app

```dart
Future<void> main() async {
  WidgetsFlutterBinding.ensureInitialized();

  await TestSdk.initialize(
    appId: 'com.example.shop',
    config: const TestSdkConfig(
      // A compile-time constant, so release builds tree-shake the
      // instrumentation away entirely.
      enabled: bool.fromEnvironment('TEST_MODE'),
    ),
  );

  runApp(const MyApp());
}
```

Then attach the observer and mark the elements worth asserting on:

```dart
MaterialApp(
  navigatorObservers: [TestSdk.navigatorObserver],  // inert when not armed
  home: Text(product.name, key: const TestKey('product.name')),
)
```

Build with `--dart-define=TEST_MODE=true` to arm it.

**Production safety** has three independent layers: a compile-time constant
the tree-shaker acts on, a runtime guard that refuses to arm in release
without an explicit opt-in, and the fact that the VM Service does not exist
in release builds at all.

## Development

```bash
dart run scripts/check_dependencies.dart   # enforce the layering rules

cd packages/flutter_testsmith && dart test test/protocol
cd packages/flutter_testsmith && dart test test/engine
cd packages/flutter_testsmith && dart test test/cli
cd packages/flutter_testsmith && dart test test/figma
cd packages/flutter_testsmith && dart test test/ai
cd packages/flutter_testsmith && flutter test test/sdk
cd examples/ecommerce_app && flutter test   # includes the defect matrices
```

Nothing in `.env` is required to build the workspace or run the test
suites - every variable gates an optional capability, and a capability
with no credential reports as unavailable rather than failing.
